What is a CRD?
Out of the box, Kubernetes only knows built-in types: Pod, Deployment, Service, ConfigMap… A CRD (CustomResourceDefinition) is how you teach the cluster a new type. You apply a CRD that says "there is now a kind called SecurityGroups, with these fields," and from that moment the Kubernetes API accepts objects of that kind, stores them, lets you kubectl get securitygroups, and lets controllers watch them.
Think of it in Python terms: the CRD is the class definition, and each CR (custom resource) is an instance of it. A CRD by itself does nothing — it's just schema + storage. What makes it do something is a controller watching instances of it (arts-controller, here).
And the relationship to Crossplane: an XRD is Crossplane's fancier flavor of the same idea — a custom type that additionally has a Composition attached, so creating an instance automatically fans out child resources. Every XR is backed by a CRD under the hood. So the hierarchy is: CRD = plain custom type + hand-written controller; XRD/XR = custom type + declarative Composition. The architect's edit reclassified SecurityGroups from the second category to the first — it's a plain custom type whose behavior comes from arts-controller's code, not from a Composition.
Decoding "living at arts.merna.sf/v1alpha1 in arts-controller-system"
That sentence packs two Kubernetes coordinates:
arts.merna.sf/v1alpha1 is the apiVersion — the type's full address, made of an API group (arts.merna.sf) and a version (v1alpha1). Groups are namespaced-by-domain so types from different teams can't collide, exactly like Go module paths or Python packages. Compare: your Workspace is merna.sf/v1alpha1 (the platform's group), while SecurityGroups is arts.merna.sf/v1alpha1 (the ARTS team's subgroup). The different group prefix is itself the ownership signal — different team, different API family. v1alpha1 means the schema is early-stage and may still change.
arts-controller-system is the namespace — the folder inside the cluster where the SecurityGroups instances are created. Namespaces group related objects and scope permissions. The convention <thing>-system means "this namespace belongs to that component's machinery." So: the five SecurityGroups objects for your workspace get created inside the ARTS controller's own namespace, where its controller and RBAC live. (Contrast: Workspace is scope Cluster — cluster-scoped, sitting outside any namespace.)

XRD vs XR vs Composition — the Crossplane trio
Crossplane extends Kubernetes so you can define your own resource types. Three pieces, and an analogy that maps cleanly to code:
XRD (CompositeResourceDefinition) = the class definition / schema. It's a YAML that tells the cluster "there shall exist a type called Workspace at merna.sf/v1alpha1, with these spec fields (friendlyName, githubOrganization, aliases…) and these status fields." You don't see "XRD" on the diagram because the diagram shows instances flowing through the system, not the type definitions — but for Workspace, SecurityGroups, and XGitHubSCIMRepositoryAccessTeam to exist at all, someone wrote an XRD for each. That's why you've heard the term: it's the schema behind every box.
XR (Composite Resource) = an instance of that class. Your ws-84d7ca42… planes-walkers object is one XR. "Product XR," "Crossplane XR," "Nested XR" on the diagram are not different technologies — they're all just XRs, and the badge words are describing their role: "Product XR" means "this one is the product, the thing users request." "Nested XR" means "this XR is created by another XR's composition rather than by a user" — a child, one level down.
Composition = the constructor logic. And to answer you directly: yes, it's YAML — a Composition resource containing a pipeline of steps (often running small functions, e.g. Go-templating or patch-and-transform). It answers the question: "when an XR of this type appears, what resources should be created from it, and how do fields map?" The four steps on the board (render-hub-cluster-resources → render-github-resources → set-status-fields → detect-readiness) are that pipeline. So nothing "calls" the Composition like a function call — Crossplane sees a Workspace XR exist and runs its Composition to figure out what children should exist. Declarative, not imperative.
Correction #1: the Composition doesn't call arts-controller
The sequence is looser than a call chain, and this is the key Kubernetes idiom — watches:

Composition step 1 renders five SecurityGroups objects into the cluster (4 tiers + sf-fedhub-{ws}). It just creates them and moves on. It doesn't invoke anything.
arts-controller is a separate program running in the cluster that has told the Kubernetes API "notify me whenever a SecurityGroups object appears or changes." That subscription is what "watches" means — a controller sitting in an event loop. When the five new objects appear, it wakes up, calls ARTS to create the Entra groups, resolves the OID via FedHub, and writes the results back into each SecurityGroups object's status (status.oid, memberEmails[], roleAssigned: Ready).
Nobody "passes a message saying it's done." Done-ness is the status fields being filled in. Anyone who cares just watches the object.

OID = Object ID — the GUID that Entra ID assigns to every group (e.g. f81d4fae-7dec-…). Names are human labels; the OID is the real key every downstream system uses to reference the group.
